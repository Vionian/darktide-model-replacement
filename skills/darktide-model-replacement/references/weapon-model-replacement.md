# Darktide weapon model replacement

Use a working native weapon with the same attachment family as the target. Record the source FBX/mesh, texture channels, target item templates, attachment prefix, generated unit, build manifest, game build, and the installed package before editing.

## Asset route

1. Inspect the source FBX in Blender. Keep the intended LOD only; remove helper meshes without materials and bake empties or object transforms into the mesh.
2. Preserve proportions. Align the guard, grip and tip to the native weapon frame with a uniform scale and rigid rotation. Do not stretch each axis independently.
3. Convert textures from the source evidence. For BC5-style normals, use R/G as tangent X/Y and reconstruct positive Z; never treat a zero blue channel as a complete normal map. Record any ORM channel mapping as a provisional assumption when the source shader is unavailable.
4. Compile an isolated GLB with the Darktide compiler. Read the resulting UNIT and material resources back, check vertex/triangle counts, bounds, UV convention, wrapper hashes, stream CRCs and dependency closure, and render a preview from the final native unit.
5. Use a stable unit path per model. If several model profiles share a package, include every unit and its closure in one manifest, or use separate Custom Assets tickets. Do not spawn a model whose package was never acquired.

## Runtime route

Match the item template and attachment prefix, then hide only the original grip/blade parts that were found in that attachment map. Spawn the replacement at the native equipment root, link the visual to that root, preserve native gameplay, and restore visibility on retire. Keep a profile registry for each model and weapon family; do not hard-code one global unit.

Weapon effects are attached through `ForceWeaponEffects`, `ForceWeaponWindSlashStageEffects`, or `PowerWeaponEffects`. Their init unit arguments may be an attachment unit, so bind effect state by `slot.unit_1p` and `slot.unit_3p`, the same roots used by replacement records. Merge bindings when stage and controller init order changes, and clear them on both controller destroy paths. Read charge thresholds from the native component/template; `special_active` is a separate activation signal.

For a visible first-person height correction, hook `PlayerUnitFirstPersonExtension.update_unit_position` after the native function and move the first-person unit root (`node 1`) by a fresh local offset. The weapon and hands are children of this root; moving `ap_aim` can be overwritten by the native placement path, while moving `ap_camera_node` moves the camera and cancels the visual adjustment. De-duplicate same-frame callbacks, restore only the pose owned by the mod, and restore on weapon change, setting change, disable, reload and world destruction. Test both a real root unit and an offline harness that asserts the root position is native position plus the selected offset.

## Effects and UI

Replacing particle names alone may leave the weapon looking like the original. For charge and enchantment, add a visible blade cover or coating mesh with a game-shader material, per-profile emissive colors, power/visibility controls, and a separate first-person custom-FOV path. Place the cover geometry just above the blade and keep the grip uncovered. Verify the actual mesh and material names used by `Unit.set_mesh_visibility`, `Unit.set_scalar_for_material`, `Unit.set_local_scale`, and the compiler's serialized UNIT scene graph. Apply the cover from the same charge controller as the native weapon. If an item variant exposes no thresholds, treat its small special-charge counter as a visible fallback tier instead of waiting for the generic 10/20 thresholds.

Expose a class-grouped UI with one weapon dropdown and a skin dropdown per supported weapon. Keep unsupported classes visible with an empty state, preserve the requested load order, and localize every setting title and tooltip. Store model selection separately from effect and first-person settings.

## Verification and installation

Run Lua parse checks and meaningful runtime harnesses with root/attachment units, both effect init orders, profile switching, and `ap_aim` pose assertions. Validate every manifest resource, artifact size/CRC, wrapper hash, stream and dependency. Keep a timestamped backup of the installed mod, load order, Custom Assets metadata, bundle database and affected bundle/stream files. Require the game to be closed before copying or patching. Run the Custom Assets patcher dry-run and final no-change dry-run, then verify that unrelated assets and bundles retain their hashes. Report offline checks separately from in-game visual evidence; logs saying resources are ready do not prove that a target mesh, cover or height offset is visible.

When adding a new model, preserve the source preview and conversion report beside the build, update the profile catalog and localization, and record which channel mappings and shader assumptions remain unverified.

## Repeatable weapon replacement procedure

1. Identify the native attachment family from the item template and inspect its grip, guard, blade and pommel units. Keep the original weapon's root, animation, collision, action logic and network identity; replace only the visual units.
2. Inspect the source FBX/GLB and preview, select the intended LOD, apply object transforms, and align guard and grip to the native frame with one uniform scale and a rigid rotation. Export a dedicated GLB and retain the source inspection and texture conversion report beside it.
3. Build the candidate into an isolated output directory. Read the UNIT, material and texture resources back. Confirm wrapper hashes, stream sizes and CRCs, geometry bounds, mesh names and dependency closure before merging it into the mod's `build.json`.
4. Register each model as a profile containing its unit path, attachment prefix, supported item templates, menu setting and effect flags. Hide only the native attachment parts actually found in the attachment map. Link the spawned unit to the native equipment root with identity local pose and preserve first-person custom-FOV handling.
5. Hook native effect controllers using both root arguments (`slot.unit_1p` and `slot.unit_3p`). Merge bindings when `ForceWeaponEffects`, wind-slash stage effects or `PowerWeaponEffects` initialize in either order, and clear every binding on both destroy paths. Use the native component's `num_special_charges` and `special_active` independently.
6. For effects that remain visually indistinguishable, keep the native gameplay events and replace their particle resources through a private manifest, then recolor only confirmed writable particle variables. Add a serialized blade cover for a persistent charge/enchantment signal; particle-name substitution alone is not evidence that the new appearance is visible.
7. Build the class-grouped menu with an independent weapon skin dropdown for each supported class, keep unsupported classes visible, and localize titles, options and tooltips. Keep model selection separate from effect brightness and first-person height.
8. Run Lua parse checks, profile/attachment/effect lifecycle harnesses, compiler UNIT validation, resource hash/CRC/dependency checks and an isolated Custom Assets patcher fixture. Before deployment, back up the installed mod, load order, registration metadata, bundle database and affected bundle/stream files. Deploy only with the game closed, run the patcher dry-run and final no-change dry-run, then distinguish those offline results from in-game visual confirmation.

## Verified Psyker force sword families and cover node names

Treat the ordinary Psyker force sword and the two-handed Blaze Force Greatsword as separate weapon families. The ordinary sword uses templates `forcesword_p1_m1`, `forcesword_p1_m2`, and `forcesword_p1_m3` with attachment prefix `content/weapons/player/melee/force_sword/attachments/`. The two-handed greatsword uses `forcesword_2h_p1_m1` and `forcesword_2h_p1_m2` with `content/weapons/player/melee/2h_force_sword/attachments/`. Keep separate selection settings and menu rows; a model for one family must not be offered for or matched against the other by a shared setting. Item templates were confirmed against the game's weapon pattern settings; the ordinary attachment family was confirmed from installed Extended Weapon Customization definitions and their base-unit paths.

When a cover mesh is serialized into a UNIT, inspect the compiled scene graph and object names independently. In the verified Khravengger UNIT, `Unit.node` scaling must use `cover_r_mesh`, `cover_g_mesh`, and `cover_b_mesh`; visibility calls use mesh objects `cover_r_mesh_p0`, `cover_g_mesh_p0`, and `cover_b_mesh_p0` (and their `_back` objects where present). Passing a mesh-object name to `Unit.node` can raise a repeated `UnitApi node failed` runtime popup from the charge update loop. Confirm both name sets from the final UNIT and exercise cover activation in a Lua harness before deployment.

## Weapon pose: detach parents before resetting the object frame

In the Langzhifei force-sword case, the old Blender scene retained a -90-degree X object rotation after baking vertices, resetting `matrix_world`, and then removing the FBX parent. The compiled UNIT's blade axis was +Y while the native ordinary force sword uses +Z. Correct mesh-coordinate bounds alone did not reveal the error. Capture the original world matrix, detach the parent, assign `Matrix.Identity(4)` explicitly to the object, then bake the desired target transform multiplied by the captured world matrix into its mesh. Verify the final UNIT using each mesh object's scene-graph transform, not raw geometry buffers alone.

For an ordinary force-sword reference, assemble native grip, hilt, blade and pommel through their actual attachment nodes. Mesh geometry indices in the inspected Bitsquid reader are one-based, node indices are zero-based, and mesh-local vertices require the mesh node's world transform. The inspected grip_01/hilt_01/blade_01/pommel_01 combination places the grip center near Z=-0.07085 m and tip near Z=0.84075 m; these are that combination's measurements, not universal constants for all grips or weapon families. Langzhifei's clean grip center and tip fitted those two landmarks with uniform scale about 0.83139. Preserve native hand/action animation and the runtime equipment root; do not reuse the two-handed greatsword's Z=0.15 datum. Retain the compiled-resource comparison and distinguish offline alignment from in-game contact/animation validation.

## Weapon dropdown crashes: shared settings and preview ownership

In the 2026-10-27 09:19:37 UTC session, selecting Langzhifei led to an engine access violation in UIUnitSpawner.spawn_unit called by the replacement mod's deferred update. The resource actually being spawned was **Khravengger on forcesword_2h_p1_m1**. Selection labels do not establish which model failed; inspect the stack locals before rebuilding the newly selected model. An engine access violation cannot be caught by Lua pcall.

The inspected EquipmentComponent._attach_settings clears and returns one shared local table for multiple components/worlds. Its first/third-person fill methods then overwrite perspective fields. VisualLoadoutCustomization.spawn_freestanding_item also reuses a shared settings table. Keeping these tables in deferred records allows later unrelated equipment calls to overwrite the saved world and spawner. Copy only needed stable fields (world, unit_spawner, is_first_person, in_editor) **before calling the native spawn function**, because callbacks may reenter equipment code before it returns. Do not retain temporary Matrix4x4/Vector3 values as persistent state.

Track each observed supported native equipment root independently, including roots currently using the original skin, so the dropdown can switch back without requiring a new equip event. Refresh only contexts owned by the changed weapon setting. Before deferred native access, verify the world against the manager's registered and disabled worlds and reject a destroyed or mismatched spawner. Invalidate native roots and attachment contexts before mark_for_deletion cleanup callbacks; keep a deletion guard through reentry. Invalidate UI spawners before their original destroy, and world contexts before WorldManager.destroy_world. Keep necessary cleanup hooks active while the mod is disabled. Checking only Unit.alive(root) does not establish that a separately retained world/spawner is valid.

For this incident, the minidump's spawn-call object argument pointed into memory containing backend JSON text rather than a native object; without engine symbols this supports invalid native ownership but does not exclusively prove which operation freed it. The installed 0.2.3 runtime reproduced the shared-table ownership defect offline. Version 0.2.4 snapshots inputs, scopes refresh and guards teardown; all 25 new preview lifecycle checks passed against the actual installation, including 40 dropdown cycles, all three ordinary force-sword marks, shared settings reuse, loading queues, callback reentry and destroyed worlds. Existing 24 runtime and 26 settings/effects tests also passed. These are offline regressions, not proof that the original engine exception has been reproduced or resolved in a live game.

Local evidence is in WeaponModelReplacement/build/preview_crash_analysis.json, preview_crash_old_installed_regression.log, deployment_preview_crash_audit.json and the installed regression logs. A Lua-only repair can preserve model/pose/material/texture/particle resources and registration byte-for-byte: back up the actual installation, permit only enumerated Lua/metadata changes, test installed paths and verify hashes. No asset recompilation or bundle repatch is needed when those resources have not changed.


## Ordinary force sword: edge roll and blue-violet special charging

Blade-axis alignment and cutting-edge orientation are separate constraints. A single-edged sword can have the correct +Z longitudinal axis and grip center while its edge faces the wrong way. For the user's Langzhifei correction, roll the mesh 180 degrees around the longitudinal axis through the calibrated grip center; preserve the forward tip, uniform scale and native equipment root. Bake the same frame into the charge coating. Use a proper rotation, not a negative-scale reflection. Native UNIT readback measured less than 0.05 mm deviation from the intended half-turn and less than 0.25 mm maximum triangle-corner quantization error.

The inspected ordinary ForceWeaponEffects._update_active reads the inventory component's special_active flag and drives native material start/stop times and flow events. A side-button weapon-special activation can set special_active=true while num_special_charges remains zero. Drive the ordinary sword's visible coating/aura from that native flag, not a raw mouse binding, Psyker peril, or only greatsword charge tiers. Stop the effects on expiry, unwield, disable and teardown. Bind eligible family controllers even if the current skin selector is original, so switching to the replacement can reuse the already-initialized controller.

Keep palettes attached to model profiles: the Langzhifei profile uses blue-violet, while Khravengger retains ice-blue. Effect wrapper contexts and particle-group owner lookup must carry the selected profile rather than a global boolean. Compile private blue-violet particle/material copies and preserve the existing ice closure; do not recolor shared ice resources. The verified violet graph uses ten effects, reuses textures through the compiler's content digests, and leaves all prior asset files unchanged except the Langzhifei UNIT and manifest. Give each palette independent enable/brightness controls.

Langzhifei's UNIT embeds three charge-coating shells above Z=0.16 m to leave the hilt uncovered. Verify both scene-node and mesh-object hashes for all channels, hide the shells immediately after spawn, and reveal them only when a live bound controller requests charging. The violet aura's emission positions are shortened to the ordinary blade's span and use the same root and first-person FOV policy as its model. Offline regressions cover zero-counter special activation, no activation from peril alone, no aura stacking, independent toggles, camera switch, expiry and original-to-replacement switching; in-game visual acceptance is a separate step.

The ordinary side-key action has a separate pre-activation particle: forcesword_p1_m1 action_activate_special starts content/fx/particles/weapons/swords/forcesword/psyker_activate_forcesword before special_active and stops it at activation_time (0.4 seconds in the inspected source). Recolor this phase separately from the persistent coating/aura. The Langzhifei design maps it to the private violet_force_staff_channel_charge swirl through the existing owner-scoped PlayerUnitFxExtension wrapper, preserving native stop ownership; its channel/husk variants are also private blue-violet copies. Do not assume a visible post-activation coating proves the windup has been recolored. Regressions exercise pre-activation while special_active=false, native stop, original-skin exclusion and unrelated-actor exclusion.

## Magenta weapon and icon: zero material resource bindings

The 2026-10-27 11:12:21 UTC session logged Failed assigning a material to slot for all four slots of unit d8736271f131b04b (Langzhifei). The screenshot showed solid magenta in both the character preview and item icon. The compiled UNIT had four named material slots but all four 64-bit resource IDs were zero, while the material resources themselves were registered and unchanged. --validate and dependency-closure checks alone accepted this because the broken UNIT manifest had an empty dependency list.

When compiling a mesh that uses darktide_material external intents, omit --no-materials: that flag skips resolving external references too. It is appropriate for a particle-only carrier, not this mesh. Enabling the material pass restored ice_cover_r/g/b and langzhifei_material_0 references and dependencies without creating new materials. Exactly 32 bytes (four resource IDs) changed in the native UNIT; all geometry, scene graph, UVs, normals, slot IDs, textures, pose and effects remained byte-identical.

Read the native material table structurally, require nonzero resource IDs, match every mesh geometry slot to its slot-to-resource entry, resolve each resource in the package and compare its wrapper hash and dependencies. Check both the base blade and all coating slots. Reproduce the former failure against the deployed backup and rerun the same check on installed files. Count populated slots separately from valid resource bindings. Resource readiness and Lua-only tests do not establish renderable materials. This fix is serialized-data evidence until confirmed in game.

## Blade-edge charging and measured two-handed size calibration

A Z cutoff alone leaves a coating across the entire blade face. For edge-only charging, inspect the blade silhouette and distinguish the real cutting edge from the spine, guard and ornament. In the verified Langzhifei frame, the smooth +Y boundary is its single cutting edge; the serrated -Y boundary is its spine. Khravengger has two cutting boundaries. Slice the actual source triangles along Z to obtain left/right Y envelopes, then clip the original surface triangles against narrow bands inside those envelopes. Interpolate normals on clipped edges and offset the resulting ribbon slightly above the original surface. Do not select whole large triangles merely because one vertex touches the edge. Do not inflate serialized ribbon nodes at higher charge tiers.

The 0.2.8 candidate uses a 5 mm single-edge band above Z=0.205 m for Langzhifei and 6 mm double-edge bands above Z=0.26 m for scaled Khravengger, with normal offsets 0.5/0.65/0.8 mm for RGB shells. These are model-specific authoring settings. Native UNIT readback confirmed the cover only occupies those bands, with approximately 2.13% / 4.01% of each weapon's surface area per shell. Keep source meshes, clipped ribbon meshes and compiled-unit geometry separately so tests compare actual authored surfaces and preserve the base pose.

Particles must follow the same envelope. The verified candidate reuses a compatible existing flash billboard in small stationary emission boxes centered 1.5 mm inside the cutting boundary, removes the old broad light/smoke draws, and caps flash size at 13 mm. Runtime energy_size is capped at one even when saved aura size and high-tier multipliers exceed one. Native greatsword stage2/stage2_loop keep their systems and stop ownership but no draw visualizers: the single mod-owned edge aura and serialized ribbon replace their broad glow. Skip writable-material controls for such drawless carriers, since former clouds no longer exist. Retain the previous incompatible-shader exclusion and per-palette resource closure; never patch billboard material IDs by hand. Validate native particle emission bounds, draw types, variable values and shader reachability rather than relying on GLTF authoring data alone.

Measure each two-handed family by assembling its actual grip/hilt/blade/pommel UNITs. The inspected 2h_force_sword and 2h_power_sword references use ap_hilt_01 (hash32 4000D158), ap_blade_01 (894173EC) and ap_pommel_01 (67E762A6). Confirm node transforms, including rotation, before composing parts; do not assume node ordering or use ordinary-force-sword dimensions. With grip_01/hilt_01/pommel_01 and blade_01/02, assembled greatswords measured about 1.411/1.435 m and relic swords about 1.359/1.361 m in local resource units. Khravengger measured 1.414 m before reduction. The user's modest-size correction applies uniform scale 0.88 around its existing grip cross-section center, yielding about 1.244 m total length for both supported families. This is a deliberate compact artistic fit, not an assertion that its shape matches either native blade.

Long grip triangles may have no vertices inside a selected hand interval. Intersect the surface with the intended grip plane rather than taking min/max of an empty vertex subset. Preserve the calibrated Langzhifei base pose and 180-degree cutting-edge roll when rebuilding only its ribbons. Native half-precision positions introduce independent old/new quantization errors; compare each compiled surface with its own unquantized source and bound scaled-old versus new error by the sum of those measured errors. A raw whole-UNIT byte-equality regression becomes invalid after intentional cover geometry changes; retain the zero-material-ID reproduction, exact current slot mapping, base-geometry checks and unrelated-resource byte comparisons.

Reproducible local evidence is in tools/blade_edge_geometry.py, build_blade_edge_assets.py, verify_blade_edge.py, verify_blade_charge.py and test_blade_charge.lua under the WeaponModelReplacement project. Their 0.2.8 results include 95 existing Lua regressions, 8 additional size-limit cases, native geometry/material/particle readback and an isolated registration fixture. The static comparison image illustrates serialized geometry and emitter placement; it does not validate native shaders, bloom, animation contact or in-game appearance. Run installed-path checks before patching and distinguish successful backed-up deployment from a pending in-game visual retest.
