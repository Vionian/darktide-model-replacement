# Darktide Model Replacement Knowledge

## Source hands and MMR workflow (2026-10-18, supersedes earlier FP experiments)

- Documented source-first method: use original-game hand geometry, weights and bone structure, then MMR to verify rest pose and motion transfer, then adapt to Darktide. Compare Daniya, Qianxia and Aemeath mechanisms together. Do not copy model-specific rest quaternions, helper names or proportions without matching the source.
- In `iter_20261018_source_hand_candidate`, the source hand remains the existing Roshia `.blend` mesh and weights. Both hands are individually rigidly aligned at the native wrist, preserving source joint distances and cross-sections. This supersedes the 0.70/0.84 digit shortening, 1.30 inflation and generic curl damping described in earlier historical notes below.
- NODE_NAME linking writes native finger positions. If generated joints differ from the native rig, that link defeats source-specific finger proportions. The tested alternative keeps native wrists/equipment and reconstructs only mod-owned hand descendants from source-length local FK and rest-basis-corrected native rotation. Never write the native driver bones. This is an explicit rest-retarget adapter, not a second correction layered over an engine-linked finger skeleton.
- MMR 5.2 BoneAnimCopy was executed in Blender 5.2.2 against 40 actual hand nodes. Use exact `native_bind.inverse() @ source_bind` rotational offsets with 90-degree rounding disabled; global position-copy is enabled only on the wrists. For seven synthetic cases, its resulting joints agree with production Lua within 2.34e-6 m and rotation matrix components within 3.31e-5. The editable project and `source_hand_audit.json` are in that candidate.
- Source rigidity was checked for 1749 vertices per hand, with maximum source rigid-map error below 2.5e-7 m; the generated `.unit` reproduces source joint spans. Runtime contact tests cover 22 synthetic cases, including rapid changes and independent thumb opposition/splay. They validate mathematical consistency, not every actual game action. The source armature has no active Action; do not claim Endfield's live gestures were imported.
- Research sources: XiaoFFGe/MikuMikuRig commit `5fbdc51183d3e76c2424dea9c47d78a02d3347f3` (`data.py`, `BoneAnimCopy.py`, `operators/RIG.py` in 5.2 branch) and Mwni/blender-animation-retargeting commit `424f08bd7e675619adf539209a1e8816c242c386` (`drivers.py`, rest alignment and optional hand/foot IK). MMR remains offline; the game receives native units and Lua only.
- Source-hand candidate deployment was checked on 2026-10-18: 106 artifact files and 7 runtime/config files match the game installation by SHA256; patcher reports 13 ready folders and a subsequent dry-run has zero pending bundle/stream/database writes. This establishes installation only; the current gameplay result has not been observed.
- Blender skeleton audit detail: initialize a new EditBone to nonzero head/tail length before assigning its world matrix. For whole-hierarchy pose assignment, use `Bone.convert_local_to_pose(..., invert=True)` with explicit parent matrices rather than reading stale parent caches. Confirm generated Blender rest matrices before comparing MMR to runtime FK.

## Evidence and build loop

- Track three distinct states: source blend, generated candidate, and package currently registered by Custom Assets. A `ready` resource count confirms package registration, not visual correctness of each texture channel or animated joint.
- Correlate screenshot timestamps with `console_logs/console-*.log` and candidate/deployment timestamps. In this workspace, Hong Kong local time is UTC+8 while Darktide log timestamps are UTC.
- Keep previews from the same built `.unit` and exported textures being evaluated. A source-material Blender render can hide errors in `.material` provider/channel wiring.
- Validate the serialized unit using FK-reconstructed world transforms, skin identity `world * inverse_bind`, geometry/material slot mapping, bounds, and winding. Static bind success does not prove animation rest-pose compatibility.

## Skinning and animation

- Distinguish vertex retarget maps from runtime node transforms. Moving geometry to a source pose while leaving `scene_graph` and `skin.inv_bind_matrices` in a different pose can look correct statically and fail under animation.
- First-person equipment contacts are driven by Darktide animation. Preserve wrist/weapon anchor nodes and prefer small, bounded finger-only corrections when the defect is finger curl. Do not move the hand root to improve a screenshot; that moves the visible grip away from the weapon.
- Daniya's `fp_twist.lua` is an axial forearm support using Daniya-specific helper nodes and a measured rest quaternion. Its algorithm is a useful reference; its axis, quaternion, and helper-node names are model-specific and must not be copied without matching Roshia's generated skeleton.
- A generated arms rig configuration is useful only if the runtime actually consumes it. Trace the model's `World.link_unit` mode and per-frame hooks before assuming a build-time config changes in-game animation.
- Synthetic idle/grip/flex poses are regression probes, not proof that every class animation, ability, reload, shield, dual-wield, or weapon family is correct.

## Materials and facial features

- Inspect material indices, source image alpha, generated `.material` provider/parent, texture channel hashes, and `build.json` together. A face that looks correct in Blender but loses iris/lash details in Darktide points to the native material path or depth/culling, not automatically to lighting.
- Keep eye/iris overlays on a known working diffuse/alpha path unless the custom PBR provider has been verified in-game for that exact material. Facial fill/emission should be isolated to face skin when eye textures disappear; excess eye emission can flatten iris detail.
- Verify alpha preservation before using opaque BC1. A texture's RGBA mode alone is insufficient; inspect alpha extrema and the material's alpha contract.
- `build.json` readiness and a correct resource count do not prove that the material references the intended diffuse texture. Inspect the material stream and the atlas in the generated candidate.

## Geometry and silhouette

- Localized clearance offsets can trade clipping for visible dents. Prefer a small, smooth global shape adjustment and compare side/front/back views before retaining it.
- For a fur/tail shell, move the attachment root separately from its grounded tip; shifting the full mesh downward can bury the tip. Compare silhouette and texture at game camera distance, not only a close-up preview.
- If source alpha cards are mapped to the wrong surface, establish which weighted cards are actually tail geometry before removing them. A replacement opaque shell must keep a plausible cross-section, layered silhouette, and source-consistent color/strand direction.

## Native equipment ownership and lobby weapon ghosts (2026-10-20)

- The Endfield replacement bodies are manually driven cosmetic units, while Darktide's weapon, shield, baton, ability and device units are already spawned and animated by `EquipmentComponent` under the native actor. A provider must not reparent those units to the cosmetic body: the native hand/weapon contract and first-person action path then remain intact.
- The old `weapon_links.lua` implementation selected `weapon`, `pocketable`, `device` and `ability` slots and called `World.unlink_unit`/`World.link_unit` to attach them to the temporary model. When streaming replaced `slot.unit_3p`, its stale entry could fail to restore because `entry.slot.unit_3p ~= retired_unit`; the retired shield/baton could remain attached to a cosmetic unit or appear beside the player in a lobby.
- Recursive `Unit.set_unit_visibility(cosmetic_body, ..., true)` makes that ownership bug visible: hidden native holstered equipment becomes a child of the cosmetic body and can be revealed on the next body refresh. The correct adapter is a compatibility no-op (`update`/`release` return without touching equipment); keep the cosmetic body manually driven and leave all equipment parents, link modes, 1P units and action state to the game.
- Reproduced before deployment on all 13 installed Endfield providers with `tools/model-work/test_native_equipment_lifecycle.py --expect-old-orphan`: manual link operations were nonzero and retired-unit orphaning was true. After replacing the 13 installed adapters, the same test reports zero manual link operations, no retired orphan, no hidden shield/baton reveal, 60 simulated streaming replacements, and untouched first-person units. Installed LuaJIT parse covered 145 Lua files; preview ownership regression still passed for 16 providers.
- This proves ownership/lifecycle behavior in a mock and does not establish every weapon's visual grip or a rendered in-game screenshot. Restart the game after deployment before judging the lobby; an old running session can retain already-linked units.

## Cryptic/Skitarius breed routing (2026-10-22)

- The game archetype `cryptic` uses `breed = "cryptic"`, so a provider that declares only `supported_breeds={human=true}` is rejected by the registry before its `matches` callback or mesh lifecycle runs. The cryptic breed's `base_unit` and `first_person_unit` both point to the same `content/characters/player/human/.../base` units as `human`, and its hit-zone/node names are the same; the different breed name is not by itself a skeleton incompatibility.
- To support the same replacement assets safely, declare both `human=true, cryptic=true` in each provider, allow both breeds in each `class_target`, and route portrait selection using the actual `archetype.breed`. Keep `ogryn` excluded. This was validated against the 16 provider declarations, 16 class targets, source archetype/breed definitions, Lua 5.1 parsing, and the replacement routing test.
- A separate `Skitarius` gameplay mod was present during diagnosis but did not hook the visual-loadout extension; its presence was not the cause of the missing replacement. Deployment still requires a game restart because provider registration and settings are initialized at load.
